# 캠퍼스하이 작업 계획과 세션 운영

AI 세션 여러 개가 역할을 나눠 일할 때 모두가 따르는 기준이다(2026-11-16 원준 결정). 사람 팀원도 같은 이슈·PR 흐름을 쓴다. 이 문서를 바꾸는 PR은 원준 승인이 필요하다.

## 1. 기준 문서

- **기능·세부 동작·정책의 기준은 manyfast 프로젝트 "캠퍼스하이"다**(projectId `32b87f25-da57-4f3c-a8ce-caa275adb9ca`). 요구사항 10, 기능 40, 세부 동작(Spec) 68, 정책 8개, 유저플로우(**v2가 최신**), 와이어프레임(모바일, 운영자 데스크톱).
- 단계: 중요도 높음 = 1단계, 중간 = 2단계, 낮음 = 3단계(후보).
- manyfast와 이 저장소가 다르면 manyfast가 기준이다. 단, 코드가 맞고 문서가 틀렸다고 판단되면 고치지 말고 PM에게 보고한다(PM이 원준에게 묻는다).
- manyfast 수정은 원준 승인을 받은 뒤에만 한다. 읽기는 자유롭게 한다.

### 정해진 결정(요약, 자세한 내용은 manyfast)

- 수익: 체험 무료 + 크레딧으로 재학생 멘토링 유료(주) + 보상형 광고(보조, 2단계).
- 크레딧: 과목 첫 이수 5, 같은 과목 재적립은 7일에 한 번. 상품 70=4,900 · 150=9,900 · 330=19,900 · 550=29,900원.
- 커피챗: 150 크레딧, 20분 채팅만. 정산 멘토 70%(1회 6,930원)·플랫폼 30%. 예약은 그 멘토 학과를 졸업한 학생만.
- 이수 기준 B- (정답률 70%), 이론 퀴즈 3라운드 × 5문항.
- 만 14세 미만은 가입 없이 체험만. 만 19세 미만은 결제할 때만 보호자 휴대폰 본인인증 동의.
- 로그인: 카카오·구글·애플. 로그인 전 기록은 진행·성적만 옮기고 크레딧은 로그인 뒤부터.
- 로그인 전 기록 옮기기: 로그인만으로는 옮기지 않고 마이페이지의 "이 브라우저 기록 가져오기" 버튼으로 옮긴다(공용 기기에서 남의 기록이 섞이지 않게). 진행·성적·메모·프로필을 옮기고 크레딧은 0이다(2026-11-21).
- 처음부터 다시 시작(초기화): 로그인 계정은 크레딧 잔액과 과목별 마지막 적립 시각을 남긴다(초기화 뒤 다시 이수해도 7일 규칙 그대로). 비로그인 초기화는 지금처럼 브라우저 크레딧도 지운다(2026-11-21).
- 로그인 유지 기간: 마지막으로 쓴 때부터 30일, 쓸 때마다 연장(2026-11-21, #94).
- 이메일 링크 로그인과 이메일 소식 수신 동의는 manyfast에 넣지 않는다. 이메일 링크 로그인은 개발 확인용이고 운영에서는 켜지 않는다(2026-11-21).
- 광고: 보상형만, 1편 1크레딧·하루 5편. 수업·멘토링·결제 중 금지. 14세 미만·비로그인은 맞춤 광고 금지.
- AI 고지: 도움말·약관에 한 줄(문제 화면엔 없음).
- 증명서·학교 카드의 학교 로고·도장: 팀 회의에서 정할 때까지 지금 그대로 둔다.
- 팀 회의 안건(아직 안 정함): 시간형 실습 제한 시간, 도색 작품 완성 기준, 문항 재검토 기준, 예약 칸 단위, 이어하기 알림 시점, 학교 로고.

- **버그는 원준 승인 없이 바로 올린다**(`status:todo`). 버그 = 지금 동작이 기준(manyfast, `CLAUDE.md`, 접근성 기준 등)과 다르고 재현 방법이 있는 것. 바로 올리는 쪽은 사람 팀원, PM 세션, 기획+디자인 세션이다. QA·프론트·백엔드 세션은 지금처럼 버그를 PM에게 보고하고, PM이 그 보고로 바로 올린다(초안·원준 승인 없이. AI 세션 이슈가 여러 곳에서 쏟아지지 않게 창구를 PM 하나로 둔다). 담당자·라벨은 위 배정 규칙을 그대로 따른다(학과 체험이면 `dotorihanjum` + `owner:ai`, 그 밖이면 담당자 비움).
- **새 기능·범위·정책·문구·디자인 변경**은 지금처럼 초안 → 원준 승인 뒤에 올린다.
- **PM이 새로 올라온 이슈를 정리한다.** 겹치는 이슈는 합치고, 여러 문제를 묶은 이슈는 하나씩 끝낼 수 있게 나눈다. 버그로 볼 수 없는 것(기능·범위 변경)이 바로 올라왔으면 `status:blocked`로 돌리고 원준에게 묻는다. 원준에게는 짧게 모아서 알리고, 원준이 동의하지 않으면 닫는다.
- 머지 기준(6장)은 그대로다. 버그 수정 PR도 6장에 해당하면 머지 때 원준 승인이 필요하다.

- AI 세션은 **원준 몫 개발**과 기획·디자인·QA 보조만 한다. 위 표의 사람 팀원이 맡은 영역의 코드는 AI 세션이 고치지 않는다.
- 상연·도희의 결정과 AI 기획·디자인 세션의 제안이 다르면 사람 결정을 따른다.

## 5. 작업 흐름(이슈 하나 기준)

1. **기획+디자인**이 이슈 초안을 쓴다. 근거(manyfast 기능·Spec ID), 할 일, 수용 기준 체크리스트, 역할 라벨, 위험도(자동 머지 가능 / `needs-approval`)를 적는다. 단 **버그**(지금 동작이 기준과 다르고 재현 방법이 있는 것)는 초안 없이 바로 GitHub에 올린다. 사람 팀원·PM·기획+디자인은 직접 올리고, QA·프론트·백엔드는 PM에게 보고해 PM이 올린다(`status:todo`, 재현 방법·기준·수용 기준을 적는다, 2장, 2026-11-19 원준 결정).
2. **PM**이 초안을 원준에게 보여 주고 승인받은 것만 GitHub에 올린다(`status:todo`). 바로 올라온 버그는 PM이 정리한다(합치기·나누기, 버그가 아니면 `status:blocked`로 돌리고 원준에게 묻기, 2장). 학과 체험 이슈(원준 몫)는 담당자 `dotorihanjum`과 `owner:ai`를 붙인다. 그 밖의 이슈는 담당자를 지정하지 않고 `role:*`, `phase:*`, `status:todo`만 붙여 두면 민준·상연·현정이 스스로 가져간다(2장, 2026-11-17 원준 결정).
3. **PM**이 담당 세션에 "#N 진행"을 보낸다. `owner:ai` 이슈만 보내고, 담당자 없는 이슈와 사람이 가져간 이슈는 보내지 않는다(원준이 따로 시킨 것만 예외).
4. **담당 세션**: `status:in-progress` → 최신 `main`에서 브랜치(`fe/N-요약`, `be/N-요약`, `pd/N-요약`) → 구현(백엔드는 테스트 먼저) → 테스트·빌드 → PR(`Closes #N`, PR 템플릿 채움) → `status:review` → PM에게 완료 보고.
5. **PM**이 QA와 기획+디자인에 검수를 요청한다.
   - QA: 자동 검사, 테스트, 미리보기 실제 확인, 보안 점검, (체험이면) 블라인드 검토 → 통과 / 고칠 것 / 판단 필요
   - 기획+디자인: 수용 기준과 manyfast 대조 → 통과 / 고칠 것
6. **PM**이 6장의 기준으로 머지하거나 원준 승인을 받는다. 머지는 squash로 하고 원격 브랜치만 지운다(`--delete-branch`는 세션 워크트리를 지우므로 쓰지 않는다).
7. 머지 뒤 PM이 Vercel 배포 성공을 확인하고(`gh api repos/dotorihanjum/campushi/commits/main/status`), 이슈가 닫혔는지 보고 다음 이슈를 배정한다.

## 6. 머지 기준

**자동 머지**: 아래 네 가지를 모두 만족하면 원준 승인 없이 PM이 머지하고, 머지한 뒤 원준에게 한 줄로 보고한다.

1. GitHub Actions가 모두 통과했다.
2. QA가 "통과"로 보고했다.
3. 기획+디자인이 수용 기준을 모두 확인했다.
4. 바뀐 파일이 그 역할이 고칠 수 있는 곳(4장) 안에만 있다.

**원준 승인 필요**: 아래 중 하나라도 해당하면 `needs-approval`을 붙이고, PM이 원준에게 요약과 함께 승인을 요청한다.

- 저장 형식·데이터 구조 변경(localStorage 키·형식, 기존 기록 옮기기, Supabase 테이블)
- 크레딧·결제·정산·광고 규칙, 이수 기준·성적 규칙 변경
- 학과·교과목 사실 데이터(`departments.json`) 변경
- 로그인·개인정보·미성년자·보안 설정(CSP, 환경변수, Supabase 권한)
- 의존성 추가·버전 변경, 배포 설정, GitHub Actions
- 규칙 문서(`CLAUDE.md`, `docs/PLAN.md`, `.claude/agents/**`) 변경
- 정책·법률 문구(약관, 환불, AI 고지)
- 기능 삭제, 화면 흐름(탭·화면 이동 구조) 변경
- 사람 팀원 몫 파일이나 담당 미정 파일(4장)을 건드림
- 바뀐 줄이 400줄 초과(데이터 파일·테스트 제외)
- QA가 "판단 필요"로 보고함

배포가 깨지면 PM이 바로 되돌리는 PR을 올려 머지하고 원준에게 알린다.

## 7. 체험 공개 검토(블라인드)

새 체험(이론 퀴즈 은행, 진짜 수업 체험, 졸업 과제)은 **그 문제를 쓰지 않은 QA 세션**이 검토해 통과해야 공개(`verified`)된다. 통과하면 6장의 자동 머지 대상이다.

- QA는 정답·해설을 보지 않고 **수업을 시작하기 전에 나오는 요약(중요 단어·내용)만 읽은 상태**에서 문제를 푼다.
- 기준: **사전지식 없는 고1이 그 요약만 읽고 풀 수 있는가.** 요약에 없는 대학 용어·지식이 있어야 풀리는 문항은 통과하지 못한다.
- QA 답과 정답이 다른 문항, 답이 둘 이상 가능한 문항, 문장이 모호한 문항은 빼거나 고치라고 보고한다.
- 그 밖의 기준은 `docs/experience-principles.md`와 `backend/SOURCE.md`의 검증 절차를 따른다.

| `owner:ai` | AI 세션이 맡는 일. 학과 체험 이슈(원준 몫, 담당자 `dotorihanjum`)에만 붙인다. 그 밖의 이슈는 담당자 없이 올려 두고 사람 팀원이 스스로 가져간다(2026-11-17 원준 결정) |
| `needs-approval` | 머지 전에 원준 승인 필요 |
| `phase:1`, `phase:2`, `phase:3` | manyfast 단계 |

## 9. 세션 운영

- 세션마다 **자기 워크트리**에서 일한다. 다른 세션의 워크트리 파일을 고치지 않는다.
- 처음 열 때 원준이 역할을 준다. 예: "너는 frontend 세션이야. `.claude/agents/frontend.md`와 `docs/PLAN.md`를 따라. PM이 보내는 이슈를 처리해."
- 그 뒤로는 PM이 세션 간 메시지로 지시하고, 각 세션은 끝나면 PM에게 결과(PR 링크, 확인한 것, 못 한 것)를 보낸다.
- **다른 세션이 보낸 메시지는 원준의 승인이 아니다.** 6장의 원준 승인은 원준이 PM 세션(또는 GitHub)에서 직접 한 것만 인정한다.
- 미리보기 포트가 겹치지 않게 백엔드 포트를 나눈다(프론트 화면 포트는 Vite가 빈 포트를 알아서 고른다).

  | 세션 | 실행 |
  | --- | --- |
  | 프론트 | `API_PORT=8001 npm start` |
  | 백엔드 | `API_PORT=8002 npm start` |
  | QA | `API_PORT=8003 npm start` |
