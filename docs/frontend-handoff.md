# 마이페이지 프론트엔드 인수인계

기준일: 2026-11-13. 기준 커밋: `c35fef8e7cfd9f03e37c69daaad2900073a4c9d9`.

이번 인수인계 범위는 마이페이지 UI와 프로필 이미지 변경 기능이다. 원격 main의 이론 퀴즈 재공개와 성적 규칙 복원 커밋 2개를 유지한 상태다. 이 변경은 마이페이지 커밋에 포함되는 신규 기능이 아니다. 로그인과 사용자 서버 저장은 구현하지 않았다. 아래 API는 후속 작업을 위한 제안이며 현재 호출할 수 없다. Supabase 사용도 추천 단계이며 확정된 의존성이 아니다.

이 문서와 기능 변경은 기준 커밋 위의 로컬 변경사항이다. 전달용 패치는 새 파일을 포함하며, 적용 방법은 전달 압축파일의 README에 있다. 패치는 커밋이나 배포를 수행하지 않는다.

전달 패키지의 `README.md`에는 원본 저장소 준비와 패치 적용 방법이 있다. `changes.patch`는 실제 변경, `source/`는 변경 파일의 사본, `verification.json`과 `verification/`은 검증 결과다. 이 문서의 패키지 내 위치는 `source/docs/frontend-handoff.md`다. 실행 명령은 저장소 루트에서 `npm start`, 테스트는 `npm test`, 빌드는 `npm run build`다. Node.js 22.12 이상과 Python 3.10 이상이 필요하다.

## 현재 저장 흐름

1. `App`은 `loadState(localStorage)`로 상태를 읽는다.
2. `loadState`와 `refreshCatalog`는 `normalize`를 호출한다.
3. 화면은 `state`와 `setState`를 받는다. `App`은 상태가 바뀌면 전체 상태를 `campushi-v2`에 저장한다.
4. `My.saveProfile`은 먼저 같은 키에 프로필을 포함한 전체 상태를 저장한다. 성공하면 `setState`를 호출하고 편집창을 닫는다. 실패하면 편집창에 오류를 표시한다.

따라서 서버 연결 때 `App`의 자동 저장만 바꾸면 프로필 편집은 여전히 브라우저에 직접 저장한다. `My.saveProfile`의 저장 성공 판단도 함께 교체해야 한다. 그 밖의 공통 자동 저장 실패는 현재 화면에 알리지 않고 메모리 상태만 유지한다.

화면 이동 기록은 별도 `sessionStorage` 키인 `campushi-stack-v2`에 있다. 사용자 데이터로 동기화할 대상이 아니다. 화면 전환은 URL 라우터 대신 `SCREENS`와 `nav.push`, `nav.reset`, `nav.back`을 사용한다.

## 현재 브라우저 데이터 형식

아래 표는 기존 `campushi-v2` 형식이다. 서버 요청·응답 규격이 아니다. 실제 기본값과 복원 규칙은 `model.js`가 기준이다.

| 필드 | 형식과 의미 | 서버 연결 시 분류 제안 |
| --- | --- | --- |
| `version` | 현재 `2` | 로컬 저장 형식 버전. 서버 revision과 구분 |
| `nickname` | 문자열. 공백 정리 후 최대 12개 유니코드 코드 포인트. 빈 값은 "나의 프로필" 표시 | 사용자 프로필 |
| `profilePhoto` | `null` 또는 JPEG data URL. 최대 200,000자 | 파일 저장소로 이전. DB에는 파일 경로 |
| `journeys` | `{ "학과id": {} }`. 현재 입학 시각은 저장하지 않음 | 사용자별 입학 기록 |
| `records` | `{ "학과id\|과목명": { grade, percent, attempts, last } }` | 과목 이수 요약. 각 시도 이력 전체는 현재 없음 |
| `notes` | 같은 과목 키의 문자열. 최대 3,000 UTF-16 코드 단위 | 과목별 마지막 한 줄 기록 |
| `drafts` | 같은 과목 키의 문자열. 작성 중인 기록 | 동기화 범위 결정 필요 |
| `plays` | 같은 과목 키의 `{ game, summary, score }`. 수업을 마치면 제거 | 중간 체험 결과. 서버 검증 증거가 아님 |
| `credits` | 0 이상의 정수. 모든 학과 공용 | 서버가 관리하는 잔액과 지급 이력 |
| `conditions`, `exempt` | 이수 조건 버전과 기존 해금 유지용 예외 | 조건 변경 시 호환성 대상 |
| `catalog` | 서버에서 받은 학과 목록 원본의 캐시 | 기존 학과 API 데이터. 사용자 소유 데이터와 구분 |
| `campus`, `studying` | 선택 캠퍼스, 대표 체험 학과 | 사용자 설정으로 동기화할지 결정 필요 |
| `current` | 지금 보고 있는 학과 | 화면 상태 |
| `onboarded`, `introSeen` | 시작 화면, 지도 인트로 확인 여부 | 기기 설정 또는 사용자 설정으로 분류 필요 |

`normalize`는 알려진 필드만 다시 만든다. 새 필드를 `initialState`에만 추가하면 복원 시 사라진다. 학과 목록 없이 `journeys`, `records`, `notes`를 먼저 `normalize`하면 유효한 학과·과목을 찾지 못해 기록을 제거한다. 계정 데이터와 학과 목록을 함께 준비한 뒤 변환하는 연결 계층이 필요하다.

과목 식별자는 현재 과목명 문자열이다. 과목명 변경 시 기록 연결에 영향을 준다. 서버에 고정 과목 ID를 도입한다면 기존 과목 키와의 대응표가 필요하다.

## 백엔드 담당자가 연결할 함수

| 사용자 동작 | 현재 연결점 | 후속 연결에서 달라지는 부분 |
| --- | --- | --- |
| 앱 시작, 새로고침 | `App`, `loadState`, `refreshCatalog` | 로그인 확인 후 계정 데이터 로드. 로컬 기록 가져오기는 별도 흐름 |
| 이름·사진 저장 | `My.saveProfile` | 사진 업로드와 프로필 저장 성공 후 화면 반영. 실패 시 편집 내용 유지 |
| 사진 선택 | `My.choosePhoto`, `prepareProfilePhoto` | 현재는 로컬 변환만 수행. 파일 업로드와 파일 교체 처리는 미구현 |
| 입학 | `Detail.enroll` | 입학 기록 저장 성공 후 진행 |
| 수업 중간 결과 | `savePlay`, `Lesson`의 완료 콜백 | 서버 검증용 체험 시작·제출 방식 필요 |
| 수업 완료 | `Lesson.finishWith`, `completeCourse` | 서버가 이수와 크레딧을 한 트랜잭션에서 처리 |
| 기록 초안 | `Lesson`, `drafts` 갱신 | 현재 400ms 지연 저장. 서버 저장 여부와 충돌 정책 결정 필요 |
| 리포트 | `reportText`, `download` | 계정의 최신 기록을 화면 상태에 반영한 뒤 기존 텍스트 생성 재사용 가능 |
| 처음부터 다시 시작 | `My`의 `reset` 확인창 | 현재는 `catalog`만 보존하고 나머지 로컬 상태 초기화. 서버 삭제 범위 확정 필요 |

`progressOf`, `isPassed`, `grandfather`, `grades.js`는 기존 진행 규칙의 기준이다. 현재 성적은 체험 결과 정답률로 매긴다. B- 이상 또는 P면 이수이며 한 줄 기록은 선택이다. 재수강하면 좋은 성적을 유지하고, 이번 시도가 이수 성적일 때 크레딧 5를 받는다. 과거 P 기록은 유지한다. 구현 예정으로 바뀐 과목의 기록은 보존하되 `progressOf`의 이수 수와 표시 대상에서 제외한다. 마이페이지 수치는 이 규칙으로 계산한다.

현재 `plays`, 성적, 크레딧은 브라우저에서 수정할 수 있다. 서버 저장 때 이 값을 그대로 신뢰하는 구조는 인증·무결성 검증을 제공하지 않는다. 기존 프론트 결과만으로 실제 체험 수행을 증명할 수는 없다.

## 사진 저장 형식 전환

`prepareProfilePhoto`는 원본을 서버로 보내지 않는다. 변환된 JPEG 문자열만 현재 로컬 상태에 저장한다. `cleanProfilePhoto`는 data URL의 형식과 길이를 검사하며 JPEG 파일 자체를 디코딩하지 않는다. 사진의 실제 디코딩은 선택 시 `createImageBitmap`이 수행한다.

현재 `profilePhoto`에 서버 이미지 URL을 넣으면 `normalize`가 제거한다. 서버 연결안은 프로필의 `photoPath: string | null`과 표시용 `photoUrl`을 구분한다. 만료되는 표시 URL은 영구 파일 경로로 저장하지 않는다. `null`이면 현재 학년 캐릭터를 표시하는 동작은 유지한다.

업로드한 사진 교체와 기본 캐릭터 복원은 모두 **저장하기** 때 확정된다. 취소한 업로드 파일, 교체 전 파일의 정리 정책은 서버 연결 작업에 포함된다. 브라우저의 사진 형식·용량 검사와 별도로 서버 측 검사도 필요하다.

## 후속 API 계약 제안

아래 경로·필드·인증 방식은 아직 합의하거나 구현하지 않았다. 현재 API는 `GET /api/health`, `GET /api/departments`, `POST /api/lesson_game`뿐이다. 아래 제안은 로그인·사용자 저장 작업의 논의 기준이다.

| 제안 경로 | 역할 | 필요한 계약 |
| --- | --- | --- |
| `GET /api/me` | 프로필·설정·진행 데이터 조회 | 사용자 식별은 검증된 세션에서 결정. 사진 파일 경로와 표시 URL 구분 |
| `PATCH /api/me/profile` | 이름·사진 변경 | 이름 규칙 일치. 사진 경로 소유권 검증. 서버가 저장한 값과 revision 반환 |
| `POST /api/me/photo-upload` | 사진 업로드 준비 | 허용 형식·용량, 업로드 대상과 파일 경로. 업로드 완료 검증 방식 |
| `POST /api/me/enrollments` | 학과 입학 | 학과 ID 검증. 같은 학과 입학은 중복 생성하지 않음 |
| `POST /api/me/course-attempts` | 수업 완료 | 과목 ID, 체험 제출 참조, 한 줄 기록, 중복 요청 식별자. 서버 검증 후 기록·크레딧 함께 반영 |
| `POST /api/me/import` | 브라우저 기록 가져오기 | 명시적 사용자 확인. 재실행 시 중복 생성 방지. 기존 서버 기록과 병합 규칙 |

서버 데이터와 로컬 상태 사이의 변환 위치는 별도 연결 모듈로 두는 안을 제안한다. 아직 해당 모듈이나 빈 API 함수는 추가하지 않았다. `api.js`의 공통 `request`는 현재 인증 처리 없이 JSON 요청을 보낸다. 헤더 또는 쿠키 기반 인증, 로그인 만료 처리는 후속 구현 대상이다.

현재 로컬 프로필 저장은 브라우저 저장 실패 때 편집창과 입력을 유지한다. 서버 연결 후 인수 기준은 서버 성공 전까지 편집창을 닫거나 "저장했어요"를 표시하지 않는 것이다. 사진 업로드 후 프로필 갱신 실패도 이 인수 기준의 대상이다. 두 기기에서 동시에 바꿀 경우의 revision 충돌 처리는 미구현이다.

## 배포·연결 제약

| 현재 설정 | 연결 시 영향 |

| `frontend/vite.config.js` | `/api` 프록시 사용. 기본 백엔드 8000. `API_PORT` 또는 `API_TARGET`으로 변경 |
| `api/index.py`, `vercel.json` | 운영은 기존 FastAPI를 Vercel 함수로 실행. 영속 사용자 저장소는 아직 없음 |

로그인 공급자, 인증 전달 방식, 사용자 DB·사진 저장소, 게스트 허용 범위는 후속 결정 사항이다. 서비스 비밀 키를 프론트 번들에 포함하는 설정은 제안하지 않는다.

## 기존 기록 이전과 삭제의 미정 사항

브라우저 기록에는 사용자 ID, 시도별 이벤트 ID, 수정 시각이 없다. 기존 데이터만으로 어느 기기 기록이 최신인지 판별할 수 없다. 전체 JSON 덮어쓰기는 다른 기기의 기록을 잃을 수 있다.

다음 항목은 구현 전에 합의할 내용이다.

- 최초 로그인 때 가져올 기록의 범위와 중복 처리. 수정 가능한 기존 크레딧의 인정 기준.
- 이름, 사진, 메모가 계정과 브라우저 양쪽에 있는 경우의 선택·병합 방식.
- 로그아웃·계정 전환 시 화면 상태, 사진, 임시 저장과 이동 기록의 정리 범위.
- 기존 **처음부터 다시 시작하기**가 계정의 어느 데이터를 삭제하는지. 로그아웃이나 회원 탈퇴와는 별개 동작.
- 게스트 모드 유지 여부, 통신 실패 중 작성한 기록의 재저장 방식.

기존 브라우저 기록은 계정 저장 성공을 확인하기 전까지 자동으로 제거하지 않는 안을 제안한다.

후속 작업의 첫 결정은 인증 방식과 영속 저장소 선택이다. 백엔드 담당자는 선택 가능한 구성을 제시하고, 제품 담당자는 게스트 허용 범위와 이전·삭제 정책을 결정한다. 그다음 프론트·백엔드 담당자가 요청·응답 형식, 인증 전달, 동시 수정 정책을 합의하고 연결을 구현하는 순서다. 이 인수인계는 그 결정을 대신 확정하지 않는다.

## 검증 범위

최신 원격 main 반영 후 프론트 테스트 72개, 백엔드 테스트 13개, 빌드와 차이 검사를 통과했다. 최종 명령 결과와 테스트 수는 전달 패키지의 `verification.json`에 있다. 전달 패키지의 `verification.json`에는 명령 결과와 원본 커밋에 패치를 적용한 별도 사본의 확인 결과가 들어 있다. `verification/`에는 테스트·빌드의 출력이 있다. 테스트 대상은 기준 커밋 자체가 아니라 패치를 적용한 코드다.

이 채팅에서 앞서 직접 확인한 로컬 UI 동작은 다음과 같다. 아래 수업 체험 확인은 퀴즈 재공개 전 커밋 `1684735`를 기준으로 수행했다. 최신 main에서 제거된 웹/파이선·자료구조 실습이 다시 공개된다는 의미가 아니다. 이 기록은 최신 자동 테스트 결과와 구분한다.

- 입학 전 학과 탐색, 실제 컴퓨터공학과 입학 후 마이페이지 변경.
- 웹/파이선프로그래밍 수업 완료 후 이수 1과목, 크레딧 5, 2학년 캐릭터 반영.
- 과목 기록창의 메모 표시와 `.txt` 리포트 내용 일치.
- 이름 저장, 사진 선택·저장·새로고침 후 유지, 기본 캐릭터 복원, 취소 시 기존 사진 유지.
- 손상된 사진 오류 표시, 375×667 화면과 키보드 Tab 이동, 초기화 확인창 취소.

위 확인에 사용한 이름·사진·수업 기록은 로컬 검증용이다. 실제 사용자 데이터와 브라우저 저장 파일은 전달 패키지에 포함하지 않는다. 스크린샷의 업로드 이미지는 저장소의 마스코트 이미지로 시험한 결과다.

로그인, 실제 사용자 DB·파일 저장소, 두 계정 접근 권한, 다중 기기 동기화, 서버 저장 실패 복구는 아직 검증할 구현이 없다.

## 서버 연결 후 인수 기준

- [ ] 계정 A의 이름·사진·기록을 계정 B가 읽거나 바꿀 수 없다.
- [ ] 다른 기기에서 로그인하면 서버에 저장한 프로필과 체험 기록이 나타난다.
- [ ] 기본 캐릭터는 계속 학년에 따라 바뀌고, 사용자 사진 선택 시에는 유지된다.
- [ ] 사진·프로필 저장 실패 때 기존 값과 편집 입력이 유지된다.
- [ ] 중복 완료 요청은 같은 시도에 크레딧을 한 번만 지급한다. 실제 재수강은 별도 시도로 처리한다.
- [ ] 기존 등급·선택 한 줄 기록·이수 예외 규칙이 서버 이전 후에도 유지된다.
- [ ] 기존 기록 가져오기를 다시 실행해도 기록과 크레딧이 중복되지 않는다.
- [ ] 로그아웃·계정 전환 때 이전 계정의 기록과 사진이 남지 않는다.
- [ ] 초기화의 서버 삭제 범위와 확인 문구가 일치한다.
- [ ] 서버 연결이 완료된 화면만 브라우저 전용 저장 안내를 계정 저장 안내로 바꾼다.
